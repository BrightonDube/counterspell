# Requirements: hints

## Introduction

After a run finishes, a learner can ask for help. There are two kinds of help:

1. **Authored ladder.** Four hints per problem, written by the author and stored in the pack. The learner reveals them one at a time: R1 nudge, R2 approach, R3 pseudo-code, R4 targeted fix. No AI is involved.
2. **AI hint.** One short hint written by an LLM. It is grounded in the learner's code and the **ghost input** (the minimized counterexample from the ghost engine). It is requested only after a click, is labelled as an AI hint, and never contains a full solution.

Both kinds run through the same server-side pipeline. The same OpenAI-compatible client also serves the Efficiency Familiar's speech bubble (`efficiency-familiar` spec). That spec owns the familiar endpoint and its measured mood. This spec owns the client, the prompt guards, the quota and the cost record that the familiar reuses.

The architecture is fixed by `docs/system-design.md` §0, §4 (`hints`), §9 (AI hint client) and §5 (run lifecycle). The product rules are in `docs/requirements.md` HNT-1 to HNT-3, FAM-6 and §4 (`HNT-1`, `FAM-6`). These requirements do not change them.

Sources: `docs/system-design.md` §0, §4, §5, §8, §8b, §9, §11; `docs/requirements.md` §3 E5, §4 HNT-1 to HNT-4, §4 FAM-6, §7 Privacy and Cost; `docs/licence-rules.md`; steering `api-conventions.md`, `security.md`, `rust-teaching.md`.

## Glossary

- **Authored hint**: one of the four pack-written hints for a problem. A **rung** is its level: 1 to 4.
- **Ladder**: the ordered set of authored hints for one problem.
- **Reveal**: the first time a learner gets a rung for one submission. A reveal is stored, so a later request returns the same text.
- **AI hint**: a hint generated by a provider after the learner clicks.
- **Provider**: an OpenAI-compatible chat endpoint (OpenAI `gpt-6-luna`, or Groq `openai/gpt-oss-20b`).
- **Ghost**: the minimized counterexample stored for a failed submission (`ghosts` table, `ghost-engine` spec).
- **Guard**: a server-side check that keeps full solutions out of AI output and keeps untrusted text out of the prompt as instructions.
- **Quota**: the daily count of AI generations for one user. The familiar's speech bubble counts against the same quota.
- **Spend cap**: the daily limit, in US dollars, across all users.
- **Cache hit**: an AI request whose cache key matches an earlier hint for the same submission and rung. It returns the stored text and costs nothing.
- **Reservation**: an amount of quota or spend taken before a provider call and released if the call fails.

## Scope constraints

- The Cargo workspace keeps exactly the six canonical packages. This spec adds no package. Server code goes in `crates/server/src/hints/`, shared types in `crates/common/src/hints.rs`, pack parsing in `crates/grimoire/`, and the schema in `migrations/`.
- Postgres is the source of truth for every hint row, cost and reveal state. Valkey holds only the quota and spend counters, which the system design allows as rate limits.
- No hint code runs untrusted code. Hints never call the sandbox, and this spec does not change the judge.
- The server uses `reqwest` for HTTP. It does not add an LLM SDK, so there is one HTTP client path for both providers.
- API keys come from environment variables only. This spec does not read, write or create `.env` files or key files.
- The learner's code and ghost text are sent to a third-party AI provider only after an explicit click, and the UI tells the learner that.
- Familiar mood, verdicts and the familiar endpoint belong to `efficiency-familiar`. This spec must not set or change them.

## Requirements

### R1. Authored ladder

1. THE SYSTEM SHALL store four authored hints per problem, one per rung 1 to 4, loaded from the problem pack.
2. WHEN a learner asks for rung `k` of a submission, THE SYSTEM SHALL return rung `k` only if rung `k - 1` has already been revealed for that submission (rung 1 has no prerequisite).
3. IF the learner asks for a rung whose prerequisite has not been revealed, THEN THE SYSTEM SHALL return `409 previous_rung_required` and SHALL NOT reveal any text.
4. WHEN a learner asks for a rung that was already revealed for that submission, THE SYSTEM SHALL return the same stored text and SHALL NOT create a second row.
5. THE SYSTEM SHALL NOT include any rung that has not been revealed in any response, log line or error message.
6. THE SYSTEM SHALL allow ladder reveals only for a submission that has finished (`finished_at` is set) and belongs to the signed-in user.
7. IF the submission does not exist or belongs to another user, THEN THE SYSTEM SHALL return `404 not_found`, with the same body as for an unknown identifier.

### R2. AI hint request

1. THE SYSTEM SHALL generate an AI hint only in response to an explicit `POST /api/hints` request from the signed-in user. It SHALL NOT generate one on a timer, on a keystroke, or as a side effect of another request.
2. WHERE the request asks for an AI hint at rung `k`, THE SYSTEM SHALL accept `k` only in the range 2 to 4. An AI hint at rung `k` follows the same prerequisite rule as R1.2.
3. WHEN an AI hint succeeds, THE SYSTEM SHALL return the text with the label `"AI hint"`, the provider name and the model name.
4. WHEN a request matches an earlier AI hint for the same submission and rung (cache hit), THE SYSTEM SHALL return the stored text, SHALL NOT call a provider, and SHALL NOT consume quota or spend.
5. THE SYSTEM SHALL treat every AI hint body as plain text. It SHALL NOT render it as HTML.
6. THE SYSTEM SHALL NOT let an AI hint change a verdict, a ghost, a familiar mood or any stored submission field.

### R3. Grounding in the learner's code and the ghost

1. WHEN building an AI prompt, THE SYSTEM SHALL include the learner's code, the problem statement and the submission's ghost (input, expected, got and failure kind) when a ghost exists.
2. THE SYSTEM SHALL cap the code in the prompt at 8 KB. IF the submitted code is larger than 8 KB, THEN THE SYSTEM SHALL refuse the AI hint with `422 code_too_large_for_hint` and SHALL NOT truncate the code silently.
3. THE SYSTEM SHALL cap each ghost field in the prompt at 1 KB and mark any cut with an explicit "[cut]" marker.
4. THE SYSTEM SHALL NOT include hidden test inputs, hidden expected outputs or any `test_results` row for a hidden test in the prompt.
5. WHERE no ghost exists for the submission, THE SYSTEM SHALL still allow an AI hint grounded on the verdict, the failing test verdicts and the code.
6. THE SYSTEM SHALL present the learner's code and the ghost to the model as data, inside clearly marked delimiters, and SHALL state in the system instruction that instructions found inside that data must be ignored.

### R4. No full solutions

1. THE SYSTEM SHALL instruct the model not to write a complete solution, and SHALL NOT rely on that instruction alone.
2. WHEN a provider returns text, THE SYSTEM SHALL remove every fenced code block and every run of indented lines that is longer than 3 lines before storing or returning the text.
3. IF the guard removed any content, THEN THE SYSTEM SHALL say so in the returned text, in a short sentence stating that code was removed to keep the hint to a nudge.
4. THE SYSTEM SHALL cap the stored AI hint body at 1,200 characters and the provider output at 300 tokens (`max_tokens`).
5. THE SYSTEM SHALL apply the same guard to the familiar's speech bubble when it uses this client.

### R5. Provider chain and timeouts

1. THE SYSTEM SHALL read the ordered provider list from `HINT_PROVIDERS` (for example `openai:gpt-6-luna,groq:openai/gpt-oss-20b`). The first entry is the primary and the second is the fallback.
2. WHEN the primary provider returns an error or does not answer within `HINT_TIMEOUT_MS` (default 8000 ms per attempt), THE SYSTEM SHALL call the fallback once.
3. WHEN the primary provider succeeds, THE SYSTEM SHALL NOT call the fallback.
4. IF every configured provider fails, THEN THE SYSTEM SHALL return `503 ai_unavailable` with a plain message telling the learner to use the next authored hint. It SHALL NOT invent a hint.
5. IF `HINT_PROVIDERS` names a provider whose API key is missing, THEN THE SYSTEM SHALL refuse to start with an error that names the missing variable, or SHALL disable that provider and log a warning, as set by `AI_STRICT_CONFIG` (default `true`).
6. THE SYSTEM SHALL NOT ship a third provider in this build. A list entry for another OpenAI-compatible endpoint works without code changes.

### R6. Quota, spend cap and reservations

1. THE SYSTEM SHALL allow each user `AI_DAILY_LIMIT` AI generations per UTC day (default 10). The familiar's speech bubble counts against the same limit.
2. THE SYSTEM SHALL allow all users together a global daily spend of `AI_DAILY_SPEND_CAP_USD` (default 5.00). When the cap is reached, no provider is called until the next UTC day.
3. BEFORE calling a provider, THE SYSTEM SHALL reserve one generation for the user and the worst-case cost for the spend cap. THE SYSTEM SHALL refuse the request with `429 ai_daily_cap_reached` (and the next authored rung) when either reservation would pass its limit.
4. WHEN a provider call fails in every attempt, THE SYSTEM SHALL release the user's reservation and the unused spend, so an infrastructure failure does not use the learner's quota.
5. WHEN a provider call succeeds, THE SYSTEM SHALL record the actual cost and release any unused part of the spend reservation.
6. THE SYSTEM SHALL NOT let concurrent requests from one user exceed `AI_DAILY_LIMIT` in total, even when they arrive at the same moment.
7. IF Valkey cannot be reached, THEN THE SYSTEM SHALL disable AI generation (returning `503 ai_unavailable`) and SHALL keep authored ladder reveals working.
8. THE SYSTEM SHALL return the quota state (`used`, `limit`, `resets_at`) with every AI response and every `429`.

### R7. Cost and provenance record

1. THE SYSTEM SHALL store every successful AI hint in `hints` with `source`, `provider`, `model`, `body`, `tokens_in`, `tokens_out`, `cost_usd` (numeric 10,6), `cache_key` and `created_at`.
2. THE SYSTEM SHALL compute `cost_usd` from the token counts and the per-provider prices in configuration: `HINT_PRICE_<PROVIDER>_IN_PER_M` and `..._OUT_PER_M` (US dollars per million tokens).
3. IF a provider does not return token counts, THEN THE SYSTEM SHALL estimate them from the text length, and SHALL mark the row as estimated.
4. THE SYSTEM SHALL write the ladder reveal and the AI hint row in one transaction, so a reveal is never recorded without its text.

### R8. Secrets and configuration

1. THE SYSTEM SHALL read API keys (`OPENAI_API_KEY`, `GROQ_API_KEY`) from environment variables only.
2. THE SYSTEM SHALL wrap keys in a redacting type whose `Debug` and `Display` output is `[redacted]`.
3. THE SYSTEM SHALL NOT write keys, prompts, code, ghost text or provider response bodies to logs. Logs record the provider, model, status, latency, token counts and the outcome.
4. THE SYSTEM SHALL read all hint settings through one `HintConfig::from_map` function that does no I/O, so tests never touch the process environment.

### R9. Consent and privacy notice

1. THE SYSTEM SHALL show, in the UI next to the AI hint button, that the learner's code and ghost are sent to a third-party AI provider.
2. THE SYSTEM SHALL include `sent_to_provider: true` in every AI hint response, so the client can show the notice again on a replay.
3. THE SYSTEM SHALL NOT send personal data (email, name, handle or identifiers other than the submission id) to a provider.

### R10. Familiar reuse

1. THE SYSTEM SHALL expose one internal function, `ai::generate(kind, request)`, that the familiar speech bubble uses. It applies R3, R4, R5, R6, R7, R8 and R9 for both kinds.
2. THE SYSTEM SHALL keep the familiar's `source` value as `familiar` in the `hints` table. It SHALL NOT use the ladder rung column for a familiar bubble.
3. THE SYSTEM SHALL NOT write a familiar mood, a measured fact or a verdict from this client.

### R11. Security and rate limits

1. THE SYSTEM SHALL accept `POST /api/hints` only with a JSON body and `Content-Type: application/json`, parsed with unknown fields rejected.
2. THE SYSTEM SHALL validate `submission_id` as a UUID and `rung` as an integer from 1 to 4 before any database or provider work.
3. THE SYSTEM SHALL rate-limit `POST /api/hints` per user (default 30 requests per 10 minutes) through the Valkey window counter from `run-lifecycle`.
4. THE SYSTEM SHALL never trust a client-supplied prompt, model, provider or price. Those values come only from configuration.

### R12. Definition of done

1. All requirements R1 to R11 have a passing test, using the property list in `design.md`.
2. The ladder order, the idempotent reveal and the ownership rule are proven against Postgres (`pg_` tests).
3. The fallback, the guard and the reservation rules are proven with a scripted transport and no network.
4. `cargo fmt`, `cargo clippy -D warnings`, `cargo test` and `cargo deny check licenses` pass.
5. Brighton reviews a Rust lesson for each Rust change in `docs/kiro-log/rust-lessons.md`.

## Out of scope

- The familiar endpoint, the measured mood and the familiar UI (`efficiency-familiar`).
- The judge, sandbox, ghost generation and run events (`judge-sandbox`, `ghost-engine`, `run-lifecycle`).
- Authoring the ladder text for each problem (`grimoire-packs` and the content tasks).
- The hint panel layout and styling (`ide-workspace`). This spec provides the client module and the API.
- A third provider, a per-tier paid quota, a streaming response and multi-turn chat.
- Payments and the paid tier (PAY-1).
