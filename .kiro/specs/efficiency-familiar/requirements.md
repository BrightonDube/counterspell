# Requirements: efficiency-familiar

## Introduction

The Efficiency Familiar is the jack-o'-lantern mascot in the IDE. After a Run or Submit it reacts to what was **measured**: whether the code was correct and, for a correct solution, how its running time grows with input size compared with the problem's declared `reference_complexity`. An LLM may add a short speech bubble, labelled as an AI hint, but words never change the verdict or the mood.

This spec builds four layers in this order:

1. **Measured layer.** The judge's bench timings (collected by `language-drivers`) go through a pure complexity fit in `counterspell-engine`, are compared with the reference class, and become a mood.
2. **Mascot.** The mood drives the existing SVG + GSAP jack-o'-lantern: five moods, a laugh burst, a crimson crack-and-burst, reduced motion, mute and hide.
3. **Speech bubble.** `POST /api/runs/{id}/familiar-hint`, once per finished run, through the shared hints client, with a templated fallback.
4. **[Stretch] Live typing guess.** A labelled guess from a web worker. It never changes the mood.

Property-based testing (PBT) with `proptest` is **enabled** for this spec. The properties are listed in `design.md` and map back to the requirements below.

Sources: `docs/system-design.md` §8b (and §4, §5, §7, §9), `docs/requirements.md` FAM-1 to FAM-6 and the Sandbox criteria, `docs/palette.md`, `docs/product-brief.md`, the steering files `product.md`, `frontend.md`, `api-conventions.md`, `sandbox.md`, `security.md`, `ghost-engine.md`, `rust-teaching.md`, and the sibling specs `run-lifecycle`, `language-drivers`, `hints`, `grimoire-packs`, `ide-workspace`, `counterspell-mcp-power`, `auth`, `ghost-engine`, `repo-skeleton`.

## Glossary

- **Measured fact**: a value the trusted judge observed: a verdict, a worker-clock timing, a fitted class, a confidence level, a ratio to a baseline.
- **Mood**: an integer 1 to 5. 1 Furious, 2 Angry, 3 Uneasy, 4 Pleased, 5 Laughing. Set only from measured facts.
- **Bench**: the timed run of a correct solution at growing input sizes. Collected by the judge under `language-drivers`.
- **Point**: one bench size `n` with its median time in nanoseconds and (when known) the relative spread of its repeats.
- **Complexity class**, or **class**: one of `1`, `log n`, `n`, `n log n`, `n^2`, `n^3`, `2^n`. These are the ids used by `reference_complexity` in packs (GRM-16).
- **Fit**: the pure function that turns points into a `FitReport`.
- **Confidence**: `low`, `medium` or `high`. A class is reported only at `medium` or `high`. `low` means "unsure".
- **Plausible set**: the classes the data cannot rule out, given the noise.
- **Reference class**: the class a pack declares as `reference_complexity`.
- **Gap**: observed class rank minus reference class rank, using the order above. 0 matches, 1 is "one class worse", negative is "better".
- **Baseline**: bench medians of a known-correct solution in the same language, stored in `problem_baselines`. Used only for constant-factor comparison.
- **Ratio vs baseline**: the geometric mean over common sizes of (learner median / baseline median).
- **Effect**: the one-shot animation the server asks for with a mood: `none`, `crack_burst`, `laugh_burst`.
- **Headline** and **badge**: the one-line and short plain-text results generated by one server-side function. The badge is what reduced motion shows.
- **Speech bubble**: the short note beside the mascot. Source `ai` (labelled "AI hint") or `template`.
- **Live guess**: the stretch, client-side, labelled guess from reading the code. Never a measured fact.
- **Attempt**: one execution try of a run (`restarted` starts a new attempt).

## Scope constraints

- No new Cargo package or crate. Code goes into `counterspell-common`, `counterspell-engine`, `counterspell-judge`, `counterspell-server` and `counterspell-grimoire`, and into `web/`. No new Rust dependency is added. Web gains `gsap` (accepted licence exception) and, for the stretch only, `web-tree-sitter`.
- Untrusted code runs only in the sandbox, as before. This spec adds no process execution. The fit and the mood function are pure.
- This spec does **not** implement bench *collection* (driver bench mode, worker timing, warm-ups, repeats, budgets, `bench_start` and `bench_point` events). That is `language-drivers` (T08, T09). This spec supplies what that work consumes and what it hands off to (R2, R3, R5, R7).
- The hint client, quota, guards, cost and `hints` table are `hints`. This spec calls `hints::ai::generate(Kind::Familiar, …)` and adds only the familiar prompt, claim guard, template and route.
- The IDE shell, docking, SSE reducer and hint panel are `ide-workspace`. This spec supplies the mascot module and the server API it consumes (design: seam table).
- Valkey stays cache and rate limits only. Postgres holds every measured result and event. Hidden inputs and expected outputs never appear in a public event, prompt or response.

## Requirements

### R1. The mood is set only by measured facts

**User story:** As a learner, I want the pumpkin's reaction to be something I can trust, so that I learn from it instead of arguing with it.

1. THE judge SHALL compute the mood exactly once per attempt, after the verdict is known, by calling one pure function, `decide`, in `counterspell-common`.
2. THE input of `decide` (`MeasuredFacts`) SHALL contain only: the verdict kind, the run mode, the bench outcome (class, confidence, status), the reference class and the ratio vs baseline. It SHALL NOT have a field for source code, AI text, browser data, a live guess or a user preference.
3. A test SHALL fail if `crates/common/src/familiar/mood.rs` mentions hint, AI, guess or speech identifiers.
4. WHEN the verdict is not Accepted, THE mood SHALL be 1 (Furious), whatever any other fact says.
5. WHEN a run ends as `failed`, `expired` or `internal_error`, THE system SHALL store no mood, emit no `familiar` event, and the UI SHALL show a calm state with no reaction. Infrastructure failure is never a Furious pumpkin.
6. THE mood SHALL be stored and streamed before any speech bubble is requested. THE speech bubble SHALL NOT be able to change it (R11).
7. THE browser SHALL change the mood only on a server `familiar` event or a stored run result. Typing, editing, switching language and the live guess SHALL NOT change it.
8. IF a stored run has no mood (a run from before this feature, or one without a measurement), THEN THE UI SHALL show the calm state and the text "No efficiency result for this run", never a positive mood.

### R2. Bench inputs, hand-off and discard rules

**User story:** As the operator, I want timing evidence that is fair and hard to fake, so that the mood does not depend on luck or on the learner's browser.

1. WHEN all tests of a Run or Submit pass and the problem declares both `[bench]` and `reference_complexity`, THE judge SHALL run bench mode (collected under `language-drivers`) and hand the points to this spec's `assess` function.
2. THE engine SHALL provide `sized_input(schema, size_param, n, seed)`, which returns one schema-valid input whose size parameter has exactly `n` elements. For `int_array` and `str` that is the length. For `matrix` it is `s × s` with `s = floor(sqrt(n))`.
3. `sized_input` SHALL be deterministic. THE bench seed SHALL depend only on (problem slug, problem version, `n`, generator version), never on the learner's code, so the learner and the baseline are timed on the same inputs.
4. `sized_input` SHALL honour element ranges, alphabets, `sorted` and `unique`. It MAY exceed the schema's length bounds for the size parameter, because bench sizes are larger than hidden-test sizes. It SHALL return an error when `unique` cannot be satisfied.
5. THE judge SHALL read the host load average before and after the bench. IF either reading is above the configured limit (default 3.0 [E]), THEN THE judge SHALL discard the bench: no complexity claim, status `discarded_host_busy`.
6. IF a bench call fails, times out, hits an output or memory limit, or loses its process, THEN THE judge SHALL make no complexity claim (status `failed`). It SHALL NOT change the verdict that the correctness tests produced.
7. IF the bench stops early (budget or per-point cap) and fewer than 3 points completed, THEN THE judge SHALL make no complexity claim (status `incomplete`). IF 3 or more points completed, THE judge SHALL fit those points.
8. THE judge SHALL persist every raw sample in `run_timings`, scoped to the attempt, and SHALL put only sizes and medians in public events.
9. Timing SHALL come from the worker's monotonic clock. The learner's program and the driver SHALL have no way to report a time.

### R3. The complexity fit (pure, in the engine)

**User story:** As a learner, I want "looks quadratic" to be said only when the data really supports it, so that I am not misled by noise.

1. THE function `counterspell_engine::complexity::fit` SHALL accept 3 to 32 points. Each point has `n`, `median_ns` and an optional relative `spread`. IT SHALL return an error for: fewer than 3 or more than 32 points, `n < 2`, `n` not strictly increasing, `median_ns == 0`, or a negative or non-finite `spread`.
2. THE model set SHALL be exactly `1`, `log n`, `n`, `n log n`, `n^2`, `n^3`, `2^n`.
3. THE fit SHALL compute three views of the same data: (a) the log-log least-squares slope with its standard error, (b) the size ratios between consecutive points, expressed per doubling of `n`, and (c) the best-fitting model by normalised residual (relative error on a log scale).
4. THE fit SHALL accept a class only when (a), (b) and (c) agree and exactly one class is plausible given the noise. Otherwise the confidence SHALL be `low` and the class SHALL be absent.
5. WHEN confidence is `low`, THE report SHALL still list the plausible classes, the model with the lowest residual (`leaning`) and the reason codes, so the UI can say what the data allows.
6. `high` SHALL require at least 5 points, a size range of at least 32×, estimated noise of at most 12%, a clear margin over every other class, a result that does not change when any one point is dropped, and a class other than `1`, `log n` and `2^n`. `medium` SHALL require at least 3 points, a size range of at least 8×, and (with 5 or more points) the same drop-one stability. [E]
7. WHEN the run mode is Run, THE confidence SHALL be capped at `medium`.
8. **Soundness.** For synthetic series generated from `n`, `n log n` and `n^2` with a fixed overhead, multiplicative noise and occasional spikes, THE fit SHALL return the true class or `low`, and SHALL NOT return a wrong class with `high` confidence. For `medium` it SHALL NOT be off by more than one class.
9. **Usefulness.** For noise-free series from `n`, `n log n`, `n^2` and `n^3` with at least 5 points spanning at least 32×, THE fit SHALL return the true class with at least `medium` confidence, so "always unsure" cannot pass.
10. THE fit SHALL be deterministic and scale-invariant (multiplying all medians by a positive constant changes neither class nor confidence), SHALL never panic, and SHALL return only finite numbers.
11. THE fit SHALL be one function with one set of constants (`FitConfig`, version `fit-1`). Judge, `counterspell-mcp` (`fit_complexity`) and Grimoire (SBX-05) SHALL all call it. No second classifier SHALL exist.
12. THE engine SHALL stay pure: no new dependency, no process, file, network or clock use, and its existing purity scan SHALL still pass.

### R4. Reference comparison and baselines

**User story:** As a learner, I want my solution compared with what the problem author expects, and with a fair idea of constant-factor speed.

1. THE judge SHALL read the reference class from the problem at run time and store it in the result, so a later edit of the problem does not change an old result.
2. THE gap SHALL be defined only when a class was reported (`medium` or `high`).
3. THE judge SHALL compare constant factors only against a baseline in the **same language**, for the **same problem version**, measured with the **same runtime image digest**. A baseline that fails any of these checks SHALL be treated as missing.
4. THE ratio vs baseline SHALL be the geometric mean of (learner median / baseline median) over the sizes both have. IT SHALL be absent when fewer than 2 sizes are common.
5. IF a problem has no `[bench]` or no `reference_complexity`, THEN THE judge SHALL skip bench mode, emit no `complexity` event, and the mood SHALL follow R5 for "no measurement".
6. IF the baseline is missing or stale, THEN the ratio SHALL be absent and the mood SHALL NOT be 5 (R5).

### R5. The five moods

**User story:** As a learner, I want the mascot's mood to follow a simple rule I can read in the "How does it judge me?" panel.

1. THE `decide` function SHALL implement this table, in this order:

| Condition | Mood | Reason code |
|---|---|---|
| Verdict is not Accepted | 1 Furious | the verdict (`wrong_answer`, `runtime_error`, `time_limit`, `memory_limit`, `output_limit`, `compile_error`) |
| Accepted, no measurement (no spec, bench discarded, failed, incomplete) | 4 Pleased | `no_bench_spec`, `host_busy`, `bench_failed`, `bench_incomplete` |
| Accepted, confidence `low` | 4 Pleased | `low_confidence` |
| Accepted, class reported, gap ≥ 3 | 1 Furious | `worst_tier` |
| Accepted, class reported, gap = 2 | 2 Angry | `two_classes_worse` |
| Accepted, class reported, gap = 1 | 3 Uneasy | `one_class_worse` |
| Accepted, class reported, gap ≤ 0, ratio absent | 4 Pleased | `no_baseline` |
| Accepted, class reported, gap ≤ 0, ratio > 2.0 | 4 Pleased | `slower_constant_factor` |
| Accepted, class reported, gap = 0, ratio ≤ 2.0 | 5 Laughing | `matches_reference` |
| Accepted, class reported, gap < 0, ratio ≤ 2.0 | 5 Laughing | `better_than_reference` |

2. WHEN confidence is `low`, THE mood SHALL NOT be lower than 4. (A low-confidence result never drops the mood by more than one step.)
3. THE effect SHALL be `crack_burst` only when the verdict is not Accepted. It SHALL be `laugh_burst` only for mood 5 on a **Submit**. It SHALL be `none` otherwise, including a Furious `worst_tier` pass.
4. A Run (samples only) MAY produce mood 5 without a burst, at `medium` confidence at most.
5. THE function SHALL be total: every possible input yields exactly one mood, one reason and one effect.
6. THE mood SHALL be non-increasing in the gap when everything else is equal.

### R6. Wording

**User story:** As a learner, I want honest words, so that I know what was observed and how sure the system is.

1. THE system SHALL generate every headline and badge in one place (`counterspell-common`), from stored facts only.
2. Results SHALL be worded as observations: "Looks quadratic, medium confidence. The reference is linear." Low confidence SHALL say it is unsure and MAY list the plausible classes.
3. THE top mood SHALL be labelled "Matches reference complexity" (gap 0) or "Scales better than the reference" (gap below 0). No string SHALL claim "optimal", "optimum", "best possible" or "fastest possible". A test SHALL scan every template.
4. Failure wording SHALL name the verdict in plain words and SHALL NOT mention complexity.
5. Text SHALL be plain text with no markup, at most 160 characters for a headline and 40 for a badge.
6. Colour SHALL NOT be the only carrier of status. Text and an icon accompany every mood.

### R7. Persistence, events and the read model

**User story:** As a learner, I want a reload to show exactly what I saw live, so that I can trust the history.

1. THE migration SHALL add to `submissions`: `measured_complexity text`, `complexity_confidence text`, `fit jsonb`, `familiar_mood smallint` (system design §4 and §8b) and `familiar_reason text`. It SHALL create `run_timings` and `problem_baselines`.
2. Constraints SHALL guarantee: mood 1 to 5; class only with `medium` or `high`; mood only on `completed` runs; and **no mood above 1 when the verdict is not `accepted`**.
3. THE judge role SHALL be able to write the new columns and insert into the new tables. THE server role SHALL NOT be able to write any of them.
4. THE columns SHALL be written in the **same transaction** as the terminal write, from the **same value** that produced the `complexity` and `familiar` events, so a reload equals the stream.
5. AFTER the terminal write, THE new columns SHALL be frozen by a trigger, like the other result columns.
6. THE judge SHALL emit `complexity` (only when a bench was measured) and `familiar` events as public events with the payloads in `design.md`. Failure `familiar` events SHALL be emitted as soon as the verdict is known, before `ghost_hunting`. Pass events SHALL follow the bench.
7. A retried attempt SHALL start with `restarted`. Rows from earlier attempts SHALL NOT affect the new attempt's result.
8. `GET /api/runs/{id}` SHALL gain `complexity` and `familiar` sections built only from stored columns. They SHALL be absent when the columns are null, never fabricated.
9. Public payloads and the `fit` column SHALL contain only sizes, medians, derived numbers, class ids, reason codes and fixed text. They SHALL contain no source, hidden input, expected output or stderr.
10. THE `fit` column SHALL be at most 4 KiB, and event payloads SHALL stay within the 16 KiB limit from `run-lifecycle`.

### R8. Baseline measurement

**User story:** As the operator, I want same-language baselines I can regenerate, so that "slower than the baseline" means something.

1. THE judge binary SHALL provide a `baseline` subcommand that runs bench mode on a pack's known-correct fixture for one language through the normal sandbox path and inserts `problem_baselines` rows.
2. EACH row SHALL record the problem slug, problem version, language, `n`, median, the engine version and the runtime image digest.
3. THE subcommand SHALL be insert-only. A changed problem version or image digest SHALL produce a new set of rows, never an overwrite.
4. THE subcommand SHALL refuse to store a baseline when the fit of the fixture is not the declared reference class at `medium` or better (the admission test, R13.2). IT SHALL say why.
5. THE subcommand SHALL run no code outside the sandbox.

### R9. Mascot presentation

**User story:** As a learner, I want the pumpkin to feel alive at the right moments and stay out of my way the rest of the time.

1. THE mascot SHALL render five moods from separate SVG path layers (eyes, mouth) for each mood, an inner glow driven by a CSS variable, and a body, using the existing jack-o'-lantern art where it exists (design: asset contract).
2. THE glow SHALL move from blood (mood 1) through ember and candle tones to bright candle (mood 5), using palette tokens only. Raw hex values SHALL NOT appear in components.
3. WHEN a `laugh_burst` effect arrives live, THE mascot SHALL play one short shake and a ring of embers with a small success-green spark, once.
4. WHEN a `crack_burst` effect arrives live, THE mascot SHALL draw crack lines, then release about 40 crimson particles with gravity over about 900 ms, then re-form. It SHALL play once.
5. THE mascot SHALL change expression and glow with a 300 ms crossfade. IF a new effect arrives within 2 s of the previous one, THEN the mascot SHALL apply the mood without the effect.
6. Effects SHALL play only for events received live in this session. A reload or a history view SHALL show the static face for the stored mood.
7. WHERE `prefers-reduced-motion: reduce` is set, THE mascot SHALL NOT load or run GSAP, SHALL swap the expression instantly, and SHALL show the badge text (for example "Matches reference complexity" or "Timeout") in place of any burst or shake. Information SHALL NOT be lost.
8. WHEN the learner mutes the Familiar, THE mascot SHALL show a static face for the current mood with no animation. THE optional sound SHALL not exist at launch.
9. WHEN the learner hides the Familiar, THE mascot SHALL collapse to a 16 px dot that is reachable and operable by keyboard, with a text equivalent available to screen readers.
10. THE mascot SHALL expose an `aria-live="polite"` text equivalent, for example "Familiar: pleased, looks linear, medium confidence, reference linear.", whether muted, hidden or reduced.
11. THE mascot SHALL never cover editor text, SHALL use only transform and opacity animation, and SHALL dispose of every timeline on unmount, route change and reduced-motion change.
12. GSAP SHALL be loaded dynamically, only when a motion effect is first needed and motion is allowed.
13. Mood colours SHALL follow the palette rules: red tones are used only for failure moods and the glow of mood 1 and 2. Status text for a passing run SHALL NOT use the danger colour.

### R10. Preferences

**User story:** As a learner, I want to mute or hide the pumpkin and switch off the AI note, and have that remembered.

1. `GET /api/me/familiar` SHALL return the caller's preferences merged with defaults: `{ muted: false, hidden: false, skin: "jack-o-lantern", speech: "auto" }`.
2. `PATCH /api/me/familiar` SHALL accept a partial JSON object with only `muted` (bool), `hidden` (bool), `skin` (`"jack-o-lantern"`) and `speech` (`"auto"` or `"off"`). Unknown fields, wrong types and bodies over 1 KiB SHALL be rejected with `400`.
3. BOTH endpoints SHALL act only on the signed-in user, SHALL need a session, and SHALL sit behind the existing origin guard.
4. THE demo account MAY change these preferences. They reset with the demo data.
5. IF the PATCH fails, THEN THE UI SHALL keep the local choice and mark it as not synced, and SHALL NOT block coding.

### R11. Speech bubble

**User story:** As a learner, I want a short plain-words explanation of my result that cannot lie about what was measured.

1. `POST /api/runs/{id}/familiar-hint` SHALL need a session and SHALL check that the run belongs to the caller. An unknown id, a malformed id and another user's run SHALL give the same `404` body. A run of the caller that is not finished yet SHALL give `409 run_not_finished`.
2. THE endpoint SHALL return a speech bubble only for runs that have a mood. A run without a mood SHALL give `422 familiar_not_applicable`.
3. THE endpoint SHALL start at most one provider generation per run, however many times it is called and however many calls overlap. A repeat call SHALL return the stored bubble or the template.
4. THE prompt SHALL be built only from: the learner's code (at most 8 KB), the stored measured result (verdict summary, mode, fitted class, confidence, plausible classes, per-size medians, ratio vs baseline), the reference class, and the public ghost fields when the run produced a ghost. IT SHALL NOT contain hidden inputs, expected outputs, the problem statement, other users' data or personal data.
5. THE prompt SHALL tell the model to explain only the measured facts, to be unsure when confidence is low, and not to name a complexity that was not measured.
6. THE endpoint SHALL call `hints::ai::generate(Kind::Familiar, …)` so the primary-then-fallback chain (`gpt-6-luna`, then Groq `openai/gpt-oss-20b`), the code-block guard, the quota and the cost record are shared.
7. THE endpoint SHALL then apply a **claim guard**: IF the text names a complexity class that is not the observed class, a plausible class or the reference class, or contains "optimal" wording, THEN THE text SHALL be discarded and the template used.
8. AN AI bubble SHALL carry `label: "AI hint"`, `source: "ai"`, `provider`, `model` and `sent_to_provider: true`. A template bubble SHALL carry `source: "template"` and no label.
9. IF both providers fail, the cap is reached, the preference is `off`, or the code is over the size limit, THEN THE endpoint SHALL return `200` with the template and a `reason`. It SHALL NOT return an error for these cases.
10. THE template SHALL be a pure function of the stored facts and SHALL be identical on every call.
11. THE endpoint SHALL NOT write to `submissions` (the server role cannot) and SHALL NOT include a mood in its response.
12. THE bubble SHALL be at most 280 characters, plain text.
13. THE UI SHALL show a one-time notice with the first AI bubble that the code was sent to a third-party provider, and SHALL show the label with every AI bubble.

### R12. Security and privacy

1. Every query SHALL include the owner predicate. Another user's run SHALL be indistinguishable from a missing one.
2. THE server role SHALL have no write access to the mood, class, confidence, fit, timings or baselines, even if the server is compromised.
3. THE judge SHALL put no source, hidden data or stderr in any public event or in the `fit` column.
4. Logs SHALL contain no code, prompt, provider body or key. They MAY contain the run id, the mood, the reason code, the provider name, status and latency.
5. Program output and the AI text SHALL be rendered as plain text. A string containing HTML SHALL appear as text.
6. THE web mascot SHALL fetch nothing except its own static assets.
7. THE bench SHALL run only in the sandbox on the rootless sandbox daemon. The server SHALL still have no Docker access.

### R13. Pack integration

1. WHEN `counterspell-grimoire validate --sandbox` runs a pack that declares `[bench]`, THE validator SHALL time the reference through the runner's `bench`, fit it with the engine fit, and report SBX-05 when the class differs from `reference_complexity` or is not confirmed. SBX-08 ("not checked") SHALL no longer be emitted once the runner implements `bench`.
2. **Admission test.** A pack's bench SHALL be enabled only when its reference passes the fit at `medium` or better in **every launch language**, through the real driver path. This catches problems whose driver or parsing overhead hides the algorithm's growth.
3. THE starter packs MAY gain `[bench]` and `reference_complexity` where they pass admission. A pack that does not pass keeps no bench and gets pass or fail reactions only.
4. A pack's bench sizes SHOULD span at least 32×, so `high` confidence is reachable. THE validator SHOULD warn when they do not.

### R14. Live typing guess [stretch]

1. WHERE this stretch ships, THE web app SHALL run heuristics in a web worker using `web-tree-sitter`, debounced to about 700 ms after the last keystroke.
2. THE worker SHALL return `{ guess_class, confidence: "low" | "med", reasons[] }`, never `high`, for Python and JavaScript at least.
3. THE UI SHALL show it as a small bubble labelled "Guess from reading your code. Run it for the real verdict."
4. THE guess module SHALL NOT import, call or be able to reach the mood state. A test SHALL enforce the import boundary.
5. THE guess SHALL NOT change the mood, the headline, the badge or any stored value, and SHALL NOT be sent to the server.
6. THE feature SHALL be switchable off and SHALL not load its parser until used.

### R15. Verification and definition of done

1. EVERY property in `design.md` SHALL have a passing test, with `proptest` regression files committed.
2. THE fit constants SHALL be calibrated against the synthetic corpus before they are frozen as `fit-1`, and the calibration report SHALL be kept.
3. ON the real stack, a known-correct linear solution and a deliberately quadratic one SHALL each be submitted at least 30 times. THE report SHALL state the distribution of confidence and mood. THE quadratic solution SHALL never reach mood 5, and no run SHALL be reported `high` with the wrong class.
4. A failing, a passing and a slow solution SHALL each be seen end to end in the IDE: stream, mascot, reload, speech bubble.
5. THE feature SHALL pass fmt, Clippy (`-D warnings`), workspace tests, database tests, web checks and web tests, and `cargo deny check licenses`.

## Out of scope

- Bench collection itself (`language-drivers`), the hint client and quota (`hints`), the IDE shell (`ide-workspace`).
- Worst-case or amortised analysis, space complexity, and problems with more than one size parameter.
- Ghost and skeleton skins, and any sound.
- The optional server endpoint `POST /api/complexity/estimate`.
- Java and C++ benches. They arrive with the stretch languages; the fit does not change.
- Rewarding or scoring users by mood (the mood is feedback, not XP).
